# MedVeda Google Play billing: root causes, fixes and verification

Audit completed: 20 October 2026 UTC. Latest hosted snapshot: **03:40:58.975947 UTC**.

**Release decision: BLOCKED BY EXTERNAL CONFIGURATION.** The deployed catalog has no verified active price tiers. Google's price-conversion endpoint returned HTTP 403, and all four Play scheduled jobs are inactive. Repository fixes passed local verification, but have not been deployed or included in a newly verified Play-installed build.

No production deployment, hosted database write, price change, purchase revocation, Play Console change, AAB upload, release publication, or real purchase was performed during this forensic audit. Hosted queries were read-only. Existing unrelated working-tree changes were preserved.

The UUID is generated by this application's diagnostic code; it is **not a Google-issued request ID**. This log event predates this audit's read-only inspection; this audit did not invoke the catalog worker.

The request originates in `supabase/functions/_shared/playCatalog.ts:61`. It runs before product PATCH, activation and readback. Consequently, this failed execution could not create its candidate product. The worker enters this creation path after a missing-product response; that is code-path evidence, not a direct inspection of Play Console.

The precise underlying permission/identity defect is **not established**. There is no evidence here that the service-account invitation is pending. Earlier owner reports describe an Active account with six permissions. The runtime service-account identity and its effective access to `in.medveda.app` have not been independently verified. Supabase secret metadata exposes digests, not the credential contents.

The intended identity recorded in earlier project evidence is `medveda-play-billing@medveda-play-billing.iam.gserviceaccount.com`, in project `medveda-play-billing`. This is an intended identity, not a verified runtime identity.

The repository requests the Android Publisher OAuth scope and guards the package as `in.medveda.app`. A successful token followed by a Publisher 403 does not prove correct Play app permissions. The empty details array does not distinguish wrong identity, app scope, API consumer configuration or another Google access restriction. This report supersedes earlier audit statements that the failing endpoint was unknown.

## B. Fixes implemented

### Android and website routing

- `mobile-app/src/config/paymentProvider.ts`: Android always selects Play, even with an incorrect Razorpay extra.
- `mobile-app/app.config.js`: rejects Razorpay configuration for Android EAS builds and Play release profiles.
- `mobile-app/eas.json`: removes the obsolete Razorpay distribution profile.
- `mobile-app/src/services/paymentService.ts:76`: rejects direct Razorpay purchase calls before authentication/provider requests when Play is selected.
- `mobile-app/src/screens/payment/PaymentCheckoutScreen.tsx:34`: blocks Razorpay checkout before its component mounts, complementing existing navigator guards.
- `supabase/functions/create-order/index.ts:30`: rejects authenticated requests declaring the native `x-medveda-app-version` header before creating orders.

The server header is a routing hint, **not platform attestation**. Older native clients that omit it cannot be distinguished from website callers through this guard. Therefore the repository fix enforces Play in the updated Android app; it cannot guarantee that every already-installed historical client stops using Razorpay. The updated build must be distributed and its installed version verified. Website callers without this native header retain the Razorpay backend path. The repository's current `website/` is informational; a real website checkout was not available for payment testing.

Existing Razorpay verification, refunds and legitimate entitlements remain available. Educational videos remain free. No configured prices were changed.

### Catalog, verification and recovery

1. `20261019150000_play_catalog_queue_fences.sql` makes ordinary enqueue insert-only. Existing leases, retry schedules and failed states survive content edits. Existing periodic stale-tier refresh and explicit admin retry remain responsible for rechecking existing jobs. Failure writes require an unexpired running lease.
2. `sync-play-catalog/index.ts` returns 503 if failure persistence errors or loses its lease, instead of claiming a recorded failure/retry.
3. `create-play-order/index.ts` distinguishes a failed current price job from a pending tier. Status lookup failures fail closed. `playBillingService.ts` gives an unavailable/support message for failure and retains preparation text for pending work.
4. `20261019151000_play_duplicate_settlement_result.sql` preserves the duplicate flag on idempotent paid-order replay. It changes the function result, not existing payment rows.
5. `verify-play-purchase/index.ts` prevents failed consumption from downgrading `consumed`, logs safe structured Google diagnostics, and rejects invalid receipt responses (400/404/410) without granting access. Permission/network outages remain recoverable verification failures.
6. `_shared/googlePlay.ts` retries transport errors, conflicts, quota and server failures; permanent OAuth authorization failures no longer automatically retry.
7. `playBillingService.ts` checks Google receipts before ending a locally cancelled order's recheck. Refunded orders remain terminal. `mobile-app/src/types/order.ts` reflects pending/refunded database statuses.

Existing operation labels and sanitized Google error-detail handling were already present in the working tree and were retained; they are not claimed as newly authored in this audit. The Google request bodies and endpoint capitalization were checked against official references rather than changed speculatively.

## D. External blockers and exact completion steps

### Google identity and authorization

The missing evidence is the **effective runtime credential identity, API consumer state and app-scoped Play permissions**. A single specific missing permission cannot honestly be named from this generic 403.

The owner/operator should perform these checks before authorizing another catalog run:

1. Confirm the runtime credential's `client_email` and `project_id` match the intended account/project. Do not copy private keys, access tokens or full service-account JSON into logs or this report. The local `diagnose-play-service-account` handler supports an authenticated, MFA-protected exact-identity check, but deploying/invoking it requires the separate production approval and review described in the existing diagnostic plan.
2. In Google Cloud Console, select the credential's actual project, open **APIs & Services → Enabled APIs & services**, and confirm **Google Play Android Developer API** (`androidpublisher.googleapis.com`) is enabled. If absent, the owner must explicitly authorize enabling it.
3. In Play Console **Users and permissions**, open that exact service-account email. Confirm Active access, no expired access, and access to **`in.medveda.app`**. Inspect **Manage store presence** for product/pricing management, plus **View financial data, orders, and cancellation survey responses** and **Manage orders and subscriptions** for the purchase/refund lifecycle. Change only a permission actually shown to be missing; do not blindly reinvite or grant broad account access.
4. After any authorized correction, verify the same runtime identity can complete the failing conversion operation for the existing INR amount. Preserve only timestamp, operation, status and allowlisted error details. If access is correct but 403 persists, escalate to Google with package, intended identity, time and operation; label the UUID as an application correlation ID.

Google documents API setup and the purchase-management permissions in [Getting started](https://developers.google.com/android-publisher/getting_started), and describes product/pricing permissions in [Play Console permissions](https://support.google.com/googleplay/android-developer/answer/9844686). A Cloud project no longer has to be linked to a Play developer account; adding a legacy “link project” step is not a justified fix.

## E. Actual payment lifecycle and security

```text
Admin-configured notes price
  → product/content eligibility and price-sync queue
  → worker: GET candidate → convertRegionPrices → PATCH missing product
  → activate BUY option → GET exact-price/IN/ACTIVE readback
  → verified tier becomes checkout-eligible

Android purchase entry point (provider always Play)
  → authenticated create-play-order and immutable order/SKU/price
  → native expo-iap product query and matching offer
  → Google Play purchase with obfuscated account and order identifiers
  → verify-play-purchase fetches Google ProductPurchaseV2
  → validate package-bound endpoint, SKU, option, user/order hashes,
    purchase state, quantity, region and refund/consumption conditions
  → atomic settle_play_purchase: payment + order + notes entitlement
  → consume purchased item; worker recovers interrupted consumption
  → entitlement-checked get-note-url → short-lived signed private PDF URL
```

The Admin Panel remains the pricing authority. Price-tier SKUs contain the INR amount and a version suffix. The conversion call obtains the regions version; the product request retains the original Admin INR money value and enables India. Existing mismatched readback is rejected, not silently repriced.

The apparently different endpoint capitalization is documented: [GET](https://developers.google.com/android-publisher/api-ref/rest/v3/monetization.onetimeproducts/get) and [activation](https://developers.google.com/android-publisher/api-ref/rest/v3/monetization.onetimeproducts.purchaseOptions/batchUpdateStates) use `oneTimeProducts`, while [PATCH](https://developers.google.com/android-publisher/api-ref/rest/v3/monetization.onetimeproducts/patch) uses `onetimeproducts`. The [conversion endpoint](https://developers.google.com/android-publisher/api-ref/rest/v3/monetization/convertRegionPrices) is `pricing:convertRegionPrices`.

Client success alone does not grant paid access. Server authentication, order ownership, Google verification and service-role settlement are required. Unique token constraints and ownership checks reject cross-order/account token reuse. Settlement and entitlement updates are transactional; client roles cannot directly execute privileged settlement. Pending purchases do not grant access. A locally cancelled order can settle when a later valid Google receipt proves payment.

Duplicate paid products are marked duplicate and do not create another successful entitlement/referral benefit. The repaired replay result preserves that classification. Consumption follows settlement; a failed consume does not undo a legitimate purchase. Google's [billing integration guidance](https://developer.android.com/google/play/billing/integrate) requires processing only PURCHASED purchases and acknowledgement within the applicable three-day window; consumption satisfies acknowledgement for consumables.

The recovery worker reconciles purchases and processes voided tokens through `reverse_play_payment`, preserving entitlement snapshots and reversing only the affected purchase. The current paginated recovery cursor uses `claim_play_recovery_cursor`; finding the older `claim_play_void_sweep` in migrations does not mean it is the current worker path. Hosted inactive recovery jobs remain a release blocker.

`get-note-url` authenticates the caller and checks access before returning a 120-second signed URL from the private notes bucket. Existing offline access checks were retained. The Razorpay server settlement path remains available for website purchases and historical recovery.

## F. Release decision

**BLOCKED BY EXTERNAL CONFIGURATION**

Confirmed repository defects described above are repaired and locally tested. The exact failing Google endpoint is established, but its effective credential/permission cause is not. Hosted catalog readiness is absent and workers are inactive. The fixes are local, and a Play-installed purchase has not been verified.

Do not treat this report as production readiness or proof that an existing installed app has changed. Complete the explicitly authorized configuration, deployment and installed-device checks above before reconsidering release readiness.
