```http
POST https://androidpublisher.googleapis.com/androidpublisher/v3/applications/in.medveda.app/pricing:convertRegionPrices
Content-Type: application/json
```

```json
{"price":{"currencyCode":"INR","units":"1","nanos":0}}
```

Authorization uses an OAuth bearer token obtained by signing with the configured service-account key, with `client_email` as JWT issuer and scope `https://www.googleapis.com/auth/androidpublisher`. The authorization value is omitted. This request is reconstructed from deployed code and the persisted job amount, not a retained wire capture.

The method, URL, request structure, and scope match [Google's conversion API reference](https://developers.google.com/android-publisher/api-ref/rest/v3/monetization/convertRegionPrices). No endpoint or scope discrepancy was found.

## What is established and what is missing

- The observed 403 comes from the Google Android Publisher conversion request. It is not a Supabase gateway rejection or an OAuth token-exchange error: the deployed request path reaches conversion only after a token is available.
- The deployed request targets `in.medveda.app`, uses the documented API base and OAuth scope, and obtains its Google credential from the named production secret.
- Secret existence and successful historical token acquisition do **not** prove the intended service-account identity. No runtime `client_email` or Google project identity was obtained.
- The event is historical. It predates this investigation and may predate the user's latest Console checks. No fresh Google conversion request was executed, so persistence of the denial after those checks is unverified.
- The current evidence cannot distinguish incorrect runtime identity from an app/account/endpoint access restriction or another Google-side configuration issue. The user's verified permissions should not be described as missing without further evidence.

## Next diagnostic boundary

The existing local `diagnose-play-service-account` implementation performs an exact email comparison after verifying a genuine admin session, admin membership, and the configured MFA requirement. It performs no Google request or database mutation. A successful HTTP 200 can be reduced to MATCH or MISMATCH; a 401/403/500 is a failed check, not identity evidence. A false comparison also covers missing/malformed JSON, so it would need interpretation alongside secret metadata.

Because this function is absent in production, using it requires a separately approved deployment and an authorized current admin session. No deployment was attempted. Even a successful MATCH would establish identity only; it would not explain the Google denial.

After runtime identity is established, the remaining diagnostic is a standalone request to the same price-conversion endpoint using that runtime credential, preserving a safely reviewed error response.
