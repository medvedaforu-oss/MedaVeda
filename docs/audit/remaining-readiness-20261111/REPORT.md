## New verified issue and correction

**DB-IDX-001 — Seven all-row FK lookup paths lacked usable indexes.** The final catalog had active-only indexes on `notes.chapter_id`, `quiz_tests.subject_id` and `videos.subject_id`, a historical success-only index on `purchases.user_id`, and entry-type/source-only indexes on `wallet_ledger.referral_id`, `order_id`, `reverses_id`. Those predicates do not cover unqualified historical ownership/FK referencing-row lookups. Root evidence: [predecessor schema inventory](evidence/schema-inventory.json), [seven failing planner cases](evidence/fk-index-red.log).

Correction: [20261111175746_all_row_foreign_key_indexes.sql](../../../supabase/migrations/20261111175746_all_row_foreign_key_indexes.sql) adds seven nonunique B-tree indexes in one transaction. It changes no rows, authorization, settlement, trigger, uniqueness exception or grants. Two conservative inventory candidates already covered by `IS NOT NULL` indexes (`referrals.first_order_id`, `order_review_flags.order_id`) were excluded rather than duplicated.

Regression: [fk-index-coverage.sql](../../../supabase/tests/fk-index-coverage.sql) tests actual PostgreSQL equality-plan index availability and is included in [run-all.sh](../../../supabase/tests/run-all.sh). [Final red/green replay](evidence/index-final-replay.log) reproduces seven failures without the correction and seven passes with it. Every public-table row fingerprint and function/grant/RLS/policy snapshot remains unchanged in the seeded upgrade. [Rollback/locking tests](evidence/index-rollback-results.json) prove precommit abort, competing-lock timeout, successful retry after verified abort, and refusal on an already-applied index. Independent review found no must-fix SQL issue; it identified a final-tree red-harness exclusion error, which was corrected and rerun. [Review](evidence/code-review.md).

**Limits:** `enable_seqscan=off` establishes available indexed access paths, not production optimizer choices, speedup, realistic-volume capacity or FK-trigger latency. Ordinary `CREATE INDEX` takes write-blocking locks retained through COMMIT; 2-second lock timeout bounds each acquisition wait and 60-second statement timeout bounds each statement, not the whole transaction. Seven builds may retain earlier-table locks for several minutes. Real sizes, disk/WAL headroom, lock workload, supported maintenance window and operator approval remain prerequisites. This is not approval for an online production index build. [PostgreSQL CREATE INDEX documentation](https://www.postgresql.org/docs/17/sql-createindex.html).
