### 1. Notes choice checkout — `20261108100000`

**Objects:** creates `public.notes_choice_checkouts`: PK/FK `choice_id → orders.id`, unique/FK `order_id → orders.id`, state check/defaults, RLS and service-only table grants; implicit PK/unique indexes. No new trigger or policy; RLS without client policies intentionally denies clients.

**Effects:** installation creates schema only. At runtime, preparation locks by wallet user then order, calls existing `create_priced_order`, cancels the Play choice, transfers its external token to exactly one priced Razorpay order and records a permanent checkout claim. This uses existing price/tax/discount/wallet reservation logic; it does not set ₹1/₹2/₹5 prices. Authorization records provider time and queues reporting without granting access. Enqueue scans existing eligible orders/refunds/compensations/events and can cause subsequent historical processing when called.

**Risks/dependencies:** requires November pricing/reservations, external-choice/tax/order snapshot columns, `payment_jobs`, refunds/capture/event infrastructure and compatible Edge recovery. Unique bindings plus user/order locks prevent a second choice reservation; an ambiguous provider CREATE still needs receipt recovery in Edge, not a second POST. Parameter/token checks are hardened further by #2. Payment creation time is not proof of the exact authorization timestamp; reporting/tax owners must accept the contract. `search_path=public` requires trusted ownership and no untrusted schema CREATE/shadow objects.

**Safety:** explicit transaction; plain CREATE TABLE makes full-file rerun fail. No historical financial DML or backfill at installation; token transfers/reservations later become durable financial workflow facts. No automatic inverse after use. **NO-GO alone.** Install in C with #2/#7/#8 after the compatibility barrier; provider approval is required before using external-choice checkout/reporting.

## Transaction, rollback and idempotency controls

All ten raw files have explicit transaction boundaries. DDL/configuration failures before COMMIT should roll back that file; previous files in a multi-file run may already have committed. Only a reviewed grouped artifact can provide A/C unit atomicity. Except #10, raw sources do not set lock/statement timeouts; approved wrappers must supply bounded per-statement, idle-transaction and total-window observation. Lock timeouts do not prove request draining. Ordinary index locks and trigger DDL affect live availability. PostgreSQL documents [index build locking and CONCURRENTLY restrictions](https://www.postgresql.org/docs/17/sql-createindex.html).

Function replacement preserves ownership and existing permissions, so explicit revokes plus **effective** role/default-grant checks matter; extra grants can survive replacement. See [CREATE FUNCTION semantics](https://www.postgresql.org/docs/17/sql-createfunction.html). Newly created service-only objects and owner-bound fulfillment are intentional; do not grant clients broad access to make a test pass.

Before commit: abort on drift, timeout, missing prerequisite, unexpected access, inconsistent financial fingerprints, lost quiescence or expired window. Confirm rollback/backend termination and absence of partial schema changes; do not retry blindly. On disconnect around COMMIT, outcome is UNKNOWN: independent metadata/source/post-state inspection must prove all-or-none, including ledger and exact final definitions. No repair or rerun as a diagnostic.

After commit: stop rollout and retain protections/gates; propose a separately reviewed forward fix or compatible rollback artifact with current preimages. There is no supplied universal down migration. Replacing a proof with an old weaker version, dropping populated choice/test objects, undoing a token index, disabling guards or downgrading bundles can lose safety/data. New provider captures/refunds/reports/consumption cannot be undone by database rollback or restore. Preserve idempotency keys, tokens, captures, inbox, compensations and original financial history. A disaster restore requires incident approval and provider reconciliation, not just SQL backup availability.

The grouped C recovery changes, final classified proof, unresolved financial/provider evidence, fresh drift checks and demonstrated recovery are material approval gates.
