# Coordinated recovery rehearsal and acceptance

Status: plan prepared; full production recovery blocker OPEN. A synthetic PostgreSQL round trip, if recorded in `evidence/synthetic-restore.json`, verifies only the stated local scope. It cannot establish recoverability of production Auth, Storage bytes, runtime configuration, provider state or production RPO/RTO. The retained October restore had a managed Auth `audit_log_entries.ip_address` compatibility failure; no new evidence closes it.

[Supabase backup documentation](https://supabase.com/docs/guides/platform/backups) confirms that database backups do not contain Storage object bytes. The [official restore guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) is the procedure reference; pin actual supported CLI/service versions and inspect their help rather than copying older command syntax. The [current changelog](https://supabase.com/changelog.md) flags CLI v3 targeting/command changes; no CLI installation, upgrade, hosted backup export or platform setting change is part of this task.

Preparation and proof must cover a coordinated manifest:

| Component | Protected material and matching acceptance |
|---|---|
| Database | Named current consistent backup/PITR point, provenance and UTC cutoff; schema/data/sequence state, roles/memberships/ACL/defaults, functions, policies, triggers, constraints/index validity, extensions and full ledger arrays. Verify authenticated checksum inventory and financial/catalog fingerprints against the accepted recovery point, not current mutable data. |
| Auth | Actual managed schema and Auth service versions; permitted users, identities, password credentials/MFA/session records and signing/key references; provider/hook/redirect/SMTP configuration. Restore all required columns and constraints without substituting minimal IDs or dropping failures. Test controlled login/refresh/MFA/expiry/account-isolation policies with inert outbound transports. Do not assume all sessions or API keys transfer unchanged; document the approved invalidation/recovery policy. |
| Storage metadata and bytes | Buckets/privacy/policies/object/version mappings at declared cutoff plus matching immutable byte inventory (path/version/size/SHA-256/encryption reference). Hash every required restored object, reconcile missing/orphan versions without deletion, and verify owner/foreign/anonymous private Notes behavior. Metadata rows or ETags alone do not certify byte integrity. |
| Runtime/configuration | Exact approved per-function archives, dependency locks and JWT settings, project endpoints/API/Auth/Storage settings, mobile/admin compatibility, DNS/webhook routing, gates, schedules and alert configuration. Restore references from escrow; keep gates/schedulers/outbound transports OFF in isolation. Never put secret values in audit artifacts. |
| Key access | Named custodian, accessible encrypted escrow/key versions and recovery identities/MFA for DB/Auth/Storage/SMTP/provider/cron/signing. Verify ability to obtain required material in isolation without exposing it or changing production keys. |
| Provider/recovery journal | Existing capture/refund/dispute/Play/void/report evidence since each component cutoff; durable provider references, idempotency keys, webhook inbox and job leases/deadlines. Track external operations whose acknowledgement may be absent locally. A database restore does not reverse provider money or consumed tokens. |

Rehearsal steps (protected production-copy access, export and target provisioning need separate authorization):

1. Name backup custodian, isolated target, restore operator, independent observer, finance/security/incident approvers and retention scope. Approve exact existing backup copy and permitted components; authorize any new export separately. Record restore point and proposed loss limits before testing.
2. Inventory PostgreSQL/extension/Auth/Storage versions and known managed-schema differences. Use a production-compatible disposable Supabase stack with production/staging routes and payment/email/push egress blocked; prove isolation. Keep crons, workers, provider transports and all purchase gates disabled. Plain PostgreSQL stubs are insufficient for this gate.
3. Verify all backup hashes/signatures, decryptability and byte-manifest coverage; inventory expected rows, ledger source arrays and private cutoffs. Reject absent/mismatched material. Record provisioning/start/finish clocks with a monotonic elapsed timer.
4. Restore roles/extensions/schema/data in the platform-supported order for those versions, including Auth and Storage metadata. Capture every exit status/error; no ignored errors, minimal Auth replacement, disabled guards or skipped NOT VALID constraints. Check sequences, owners/ACL/RLS/functions/triggers/indexes/constraints and all original ledger entries.
5. Restore matching Storage bytes/versions and config/key references into isolated services. Verify all required object hashes and metadata joins, privacy and controlled access. Inventory missing/orphan objects; no cleanup. Test actual permitted identities/session policy and critical Notes paths with no real email or provider side effect.
6. In isolation apply exact approved A→B→C→D candidate sequence and repeat independent preservation/security/compatibility checks. Pin hosted service/cache behavior and measure lock/build times on representative data. Synthetic local tests supplement this step. No financial replay over copied real history is authorized by this plan.
7. Finance builds a per-provider gap journal from each backup cutoff through incident/recovery cutoff. Classify already-observed external effects, late deliveries and ambiguous acknowledgements using existing provider truth. Model duplicate delivery, full/partial refund, dispute outcomes and ownership reversals with inert fixtures. Propose each real correction/replay separately; never create a second payment or blindly refund/report/consume/replay because local acknowledgement is missing.
8. Record measured component cutoffs and end-to-end provisioning/import/verification/reconciliation times. Obtain independent security/finance/restore acceptance against exact evidence digests. Keep production restore, ingress/worker resume and payment activation separately gated. Retain isolated evidence under the approved policy.

The earlier proposed financial DB RPO ≤5 minutes and critical service RTO ≤4 hours remain **unaccepted targets**, not measurements or promises. Owner must approve them or explicit alternatives. Compute each component's recoverable lag; the oldest required component and coordinated consistency limit the recovery claim. Measure RTO from incident declaration through reconciliation and acceptance, not just `pg_restore`. Require zero unexplained financial differences after provider reconciliation. Any missing byte, unsupported Auth import, unavailable key or unmet target fails acceptance; no blocker closes on backup file existence alone.

Required signed result: exact target/copy and manifest digest, all component cutoffs, full import/validation logs, object coverage, Auth/Notes acceptance, provider gap journal disposition, measured accepted RPO/RTO, residual risks, observer and owner approvals.
