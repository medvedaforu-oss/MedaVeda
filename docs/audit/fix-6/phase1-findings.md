## MOB-12 — exact storage behavior

Primary source: `mobile-app/src/config/secureSessionStorage.ts:40–131`. Only production import/caller is `mobile-app/src/config/supabase.ts:16,33`, passed as Supabase `auth.storage`; no app code calls adapter methods directly. `loginLockout.ts` and `SplashScreen.tsx` mention it in comments only. `scripts/remaining-audit-selftest.cjs` loads it with mocked stores for publication tests.

The installed Supabase client derives `sb-<hostname-first-label>-auth-token` (`@supabase/supabase-js/src/SupabaseClient.ts:325`). Installed auth-js `lib/helpers.ts:124–152` JSON-serializes before `storage.setItem`, parses returned text and treats invalid JSON as absent. `GoTrueClient.ts` reads during initialization/session loading/refresh, writes on sign-in/recovery/refresh, and removes on sign-out. Its `_saveSession` stores the whole session because no separate `userStorage` is configured; `_removeSession` also removes `-code-verifier` and `-user`. PKCE helpers use the same adapter for the code verifier, which is JSON-encoded text, not a session. Migration must account for those auxiliary values, not assume every key contains session JSON.

Native v2 publication is exactly JSON `{version:2,generation,ciphertext}`. `generation` is 16 random bytes encoded as 32 lowercase hex characters. Each write creates a **fresh 32-byte AES key**, encrypts UTF-8 with `aes-js` AES-256-CTR and counter initialized to **1**, then hex-encodes ciphertext. There is no nonce field, MAC, tag or AAD. Fixed counter 1 is not demonstrated counter reuse because keys are freshly generated for each publication. The envelope parser checks version, generation shape and even-length lowercase hex; it does not bound size or authenticate any field.

SecureStore stores the 64-character key under `secure-<storage-key>.<generation>` after replacing unsupported storage-key characters with `_`. The previous installed format is bare hex ciphertext with its key at `secure-<storage-key>`; reads support it. `getItem` does not migrate; the next successful `setItem` publishes v2. Sanitization can collide for arbitrary keys, although the actual project storage keys use the supported alphabet.

All get/set/remove operations serialize **per storage key within this JS instance**, using a promise map that recovers from a prior rejected operation. This is not a cross-process or cross-key transaction. Write order: read old blob → create generation/key → persist generation key → publish full blob in AsyncStorage → best-effort delete prior generation key. Publication is the commit point. A rejected/ambiguous AsyncStorage write retains old and new key generations. A restart follows whichever generation the durable blob names. Orphan keys are possible; there is no complete orphan inventory/garbage collector. `encryptionKey.fill(0)` occurs after successful key persistence; it does not erase JS strings, cipher internals or copies, and does not run if that key persistence rejects.

Removal reads blob, **unpublishes AsyncStorage first**, then deletes that generation's key. The delete is awaited without a catch: cleanup can reject even though publication is already gone. A malformed envelope can also make removal reject after unpublication. Failed unpublication leaves the key intact. Web explicitly bypasses encryption and uses plaintext AsyncStorage for get/set/remove.

Failure boundaries are narrower than “never throws”: malformed envelope, invalid/missing key and decrypt/UTF-8 exceptions return null; **AsyncStorage reads and SecureStore reads/writes can reject** outside those catches. Locked/unavailable SecureStore preserves the blob and keys. Supabase helpers parse JSON but JSON validity is not authentication; shape validation cannot reject a controlled change preserving the shape. `generationOf` also assumes parsed object access succeeds and catches errors at the read boundary. No tag is checked anywhere.

Owner isolation is **project/storage-key isolation**, not per-account cryptographic isolation. A and B use the same project slot, replaced on successful auth writes. The adapter has no owner ID, auth epoch or subject check; app auth lifetime guards are separate. Copying a complete valid stored generation can replay a session if its key still exists. Copying only a blob to another project normally fails key lookup, but v2 cryptographically binds neither storage name nor owner. AEAD will not itself establish which account the user intended to use or revoke server sessions.

### Required migration, rollback and threat boundaries

An attacker who can modify app-private AsyncStorage includes a rooted/jailbroken device operator, someone with an applicable writable backup/restore/debug path, or code already executing with app privileges. Ordinary sandboxed apps cannot normally edit it. V2 protects confidentiality against storage-only reading when the SecureStore key remains inaccessible; it does **not** authenticate ciphertext/metadata. Known-plaintext same-length modifications are possible. This does not produce a valid server signature, bypass Supabase RLS or establish a remote exploit. Fully compromised runtime/key access is outside protection of either v2 or v3. Deletion remains a denial-of-service capability; authenticated encryption does not itself stop replay of previously valid publications.

V3 must have bounded strict schema, explicit algorithm/version, fresh 256-bit generation key, random 96-bit nonce, ciphertext, 128-bit tag and canonical AAD binding app/domain, exact storage key, algorithm/version and generation. Authenticate before decoding plaintext or trusting user fields. Verify subject using the server when migrating legacy/v2; local JSON/JWT decoding is insufficient. Preserve per-key serialization and key-first → publication → old-key-cleanup ordering. Unknown v3 or failed authentication must never downgrade to CTR. Persisting a v2 shadow for old binaries would preserve the tampering problem.

Migration refresh must be integrated with SDK auth lifecycle, not a recursive `getItem`→`refreshSession` call. Capture owner/auth lifetime, refresh through Auth, bind the validated response to that lifetime, then publish; reject stale A→B→A results. Offline/transient refresh failure defers conversion without erasing v2; definitive server revocation signs out. PKCE and auxiliary strings need a distinct migration path (or explicit expiry/restart of the pending flow), since they cannot be validated by session refresh. No automatic bulk logout is recommended.

Tag mismatch, wrong context, corrupt/unsupported envelope or missing generation key must return **null/signed-out without crashing**, with no fallback decryption. Native “temporarily locked/unavailable” errors must preserve durable data and yield a controlled retryable auth outcome; do not erase keys as corrupt. Bound/catch parse, native crypto and UTF-8 failures at the auth/UI boundary. Do not log envelope/key/token contents. Test all tag/nonce/AAD/version/generation changes, cross-key substitution, legacy refresh/offline/revocation, ambiguous publication, get/set/remove concurrency, key-loss/locked store and actual restart on both platforms.

Rollback must retain a qualified v3 reader. The current reader returns null for v3, as reproduced. Once old keys are removed, reverting to old code can force login; this cannot honestly be promised transparent. Agree on bridge release versus accepted re-login before publishing v3. No envelope has been changed in Phase 1.

## MOB-08 — delivery trace and enforceable behavior

Source trace: `utils/notificationPreferences.ts`, `screens/notifications/NotificationPreferencesScreen.tsx`, `services/notificationsService.ts`, `services/studyReminderService.ts`, `services/pushNotifications.ts`, `services/notificationRouting.ts`, admin `pages/Notifications.tsx` / `services/notificationService.ts`, sender `supabase/functions/send-push-notification/index.ts`, and registration SQL `20261114040000_fix3_content_push_and_delete_guards.sql:43`.

Preferences are a single **device-local, unscoped** AsyncStorage object at `medveda:notifications:preferences`. They are not keyed by authenticated owner and are not synchronized to the server. Six toggles cover new_notes/new_video/offer/payment_success/exam_reminder/app_update; defaults are true. Failed/malformed reads return defaults; exact boolean false is the mute check. Writes serialize read-modify-write and propagate errors. Shared-device A/B users inherit the same saved choices. Read/archive IDs are also device-local. No server preference table or category registration field appears in the traced path.

Feed reads active public `notifications` rows, maps row `type`, then filters against those local preferences. This changes visible rows/unread badges only; the public feed remains readable under its active-broadcast policy. Sender rejects any present `targetUserIds` before broadcast reservation. Fix 4 reservation RPC atomically persists one public feed row with top-level type and one admin/request ID; retries return stored outcomes. Never put private payment/recipient text in that feed.

Foreground remote delivery reaches the notification handler installed by `studyReminderService`. It rejects targeted-looking payloads/repeated identifiers, looks up **`notification.request.content.data.type`**, then consults local category preferences for banner/list/sound; badge is false. Unknown/missing category is shown. Independently scheduled study reminders have no category data and retain their separate time/enabled behavior.

**Reproduced contract gap:** the admin composer sends `{title,body,type,requestId}` without `data`; sender validates top-level `type` but initializes `data={}` and sends Expo messages as `{to,title,body,data,sound:'default'}`. It never injects the validated type into data. Thus a usual admin Offer is hidden from the feed but is **untyped to the foreground handler and still presents**. Even supplied `data.type` is not bound to validated top-level type. `announcement` and `quiz` are valid sender/admin types without corresponding preference toggles. [notification-readonly-probe.txt](notification-readonly-probe.txt) executes the actual foreground handler with synthetic data and `offer=false`: `{type:'offer'}` is suppressed, `{}` presents. This proves the local handling difference and source contract mismatch; no Expo/provider call was made.

Background/killed delivery: the sender transmits a notification payload with title/body/sound. The OS can display it before JS executes. There is no app background task registration/filter contract in the traced source. A tap reaches `setupNotificationResponseListener`: live listener plus last killed-app response, clear/deduplicate, broadcast-only allowlisted destination, pending through login/onboarding, account-change fencing. Tap routing does not reverse prior display and does not apply category mutes. Android force-stop and iOS termination/background restrictions further limit any JS delivery guarantee. [SDK57 Notifications documentation](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/) distinguishes receipt, presentation and responses; foreground handling is not a server delivery filter.

Registration sends only `p_token` and `p_platform` with the captured owner's bearer token. `register_push_token` derives `user_id=auth.uid()`, validates platform/token, rate-limits, locks that user, evicts oldest excess and upserts token ownership/platform/updated_at. Stored token records include their existing ID/timestamps; no categories, preference version, consent scope or installation ID is registered. Expo project ID is used locally to obtain the Expo token; the native FCM token is not saved in this Expo-token table. Logout attempts token deletion; transient registration failures are retried on foreground/token changes. Sender currently selects **only expo_push_token**, pages every token and never joins owner preferences. Ticket acceptance is not device delivery proof.

Today enforceable: local feed filtering; foreground filtering **when matching category data exists**; separate study-reminder scheduling/cancellation; broadcast/tap allowlist boundaries. Today unenforceable: promised per-category suppression for ordinary sender payloads, background/killed remote alerts, cross-device/account preference sync, or retracting already submitted/in-flight pushes. OS permission/channel controls can disable OS notifications independently; current channels do not implement these six categories.
