# MedVeda backup restore audit — 2026-10-23

**Final verdict: BLOCKED for a complete rollback.** The application tables passed an isolated restore and integrity check, but the complete `data.sql` restore failed against the cached Supabase PostgreSQL image because its managed Auth schema differs from production. Production rollback is **not verified**. No production connection or write was made.

| Check | Result | Evidence |
| --- | --- | --- |
| Original backup integrity | PASS | `sha256sum -c SHA256SUMS.txt`: `roles.sql`, `schema.sql`, and `data.sql` each `OK`. Original files were read only. |
| Capacity and compatibility | PASS for local trial | 6.4 GiB host RAM, about 1.5 GiB available; 7.8 GiB disk free; Docker had no active containers or volumes. Cached `public.ecr.aws/supabase/postgres:17.6.1.147` (1,703,948,080 bytes, Linux amd64) matched the dump's PostgreSQL 17.6. No image download. |
| Isolation | PASS | Disposable `medveda-restore-20261023` container used `--network none`, no port or volume mounts, a 1 GiB memory limit, and one CPU. All restore commands targeted its local `postgres` database via `docker exec`. |
| Roles and schema | PASS | Six required extensions were available: `pg_cron`, `pg_net`, `pg_stat_statements`, `pgcrypto`, `supabase_vault`, `uuid-ossp`. The first roles attempt as `postgres` failed because `supabase_admin` is reserved; retry with the image's existing `supabase_admin` superuser passed. Unchanged `schema.sql` then passed with `ON_ERROR_STOP=1`. |
| Complete data restore | **FAIL / compatibility BLOCKED** | Unchanged `data.sql` stopped with `ERROR: column "ip_address" of relation "audit_log_entries" does not exist`. The cached image's managed `auth` and `storage` schemas lack many dump columns and tables. A full data restore was not achieved. |
| Application data and counts | PASS, partial scope | A generated stream loaded all 46 original `public` COPY sections, two public sequence values, and only 27 Auth user IDs needed for FK checks, in one disposable transaction. This did not restore Auth account fields, sessions, or Storage metadata. All 46 application table row counts matched the dump: 645 expected and 645 actual, zero mismatches. Representative actual counts: `profiles` 26, `courses` 5, `chapters` 146, `notes` 29, `orders` 27, `payments` 15. |
| Application integrity | PASS, partial scope | Dump requests `session_replication_role = replica` to load circular references. After loading, an explicit join check across all 65 `public` foreign keys found zero orphan rows. All 65 FK constraints were marked valid; the restored schema also had 46 primary keys, 9 unique constraints, and 76 check constraints marked valid. This does not validate omitted managed Auth/Storage data or application behavior. |
| RLS, grants, functions | PASS, structural | RLS enabled on all 46 public tables; 46 public policies and 118 public functions present. `anon`, `authenticated`, and `service_role` each had SELECT/INSERT/UPDATE/DELETE privileges on all 46 public tables and EXECUTE on all 118 public functions in this local image. Effective access depends on RLS policies and function behavior, which this audit did not exercise as application clients. |

The dump contains 79 COPY sections: 46 `public`, 26 `auth`, and 7 `storage`. The nonempty managed sections contain 256 Auth rows (including 27 `auth.users`) and 58 Storage metadata rows (including 55 `storage.objects` and 3 `storage.buckets`). Thus Auth and Storage **table rows are partly included** in `data.sql`, but their managed schema definitions are absent from `schema.sql`, and the full rows could not be restored in this image. The backup does not contain uploaded object bytes, project and Auth provider configuration, external secrets or signing/payment credentials, or deployed Edge Functions. No personal data or credential values were printed in the audit.

**Recovery limitation:** the three SQL files alone cannot demonstrate a complete production rollback. A compatible disposable Supabase environment with matching managed Auth/Storage schema is needed to restore all 79 COPY sections and validate their constraints; uploaded files and external configuration need separate recovery evidence. No plan upgrade, migration, deployment, build, or production change was performed. The disposable container and temporary logs were removed after this audit.
